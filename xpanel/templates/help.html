ОСНОВА

Профиль, Inbound и точка входа

Три похожих термина обозначают разные уровни настройки.

Профиль

Серверная схема, которую SG-Panel применяет целиком. Одновременно выбран один профиль.

Inbound

Реальный входящий обработчик Xray внутри выбранного профиля.

Точка входа

Публичная комбинация адреса, порта и параметров, по которой подключается клиент.

i

Сначала измените настройки, затем нажмите «Проверить конфигурацию». Кнопка применения становится доступна только после успешного теста временной копии базы и итогового config.json.

CLUSTER И SG-NODE

Полная установка, подключение и первый профиль

Controller и SG-Node подключаются в пять последовательных шагов. Полная установка Node и её регистрация в Cluster — две разные операции.

Чистая Ubuntu→Подготовленная SG-Node→Heartbeat→VLESS REALITY :64441
Cluster Controller

Полная SG-Panel с центральной базой, карточками Node, очередью заданий и административным интерфейсом.

SG-Node

Удалённый сервер с Agent, Worker, Xray и необходимым runtime. Вторая SG-Panel на нём не устанавливается.

Независимая работа

Если Controller временно недоступен, уже развёрнутый Xray-профиль и клиентский трафик Node продолжают работать.

Перед началом

  1. Подготовьте отдельный сервер с чистой поддерживаемой Ubuntu LTS и доступом sudo.
  2. Убедитесь, что Node может исходящим соединением открыть адрес и порт Controller.
  3. Разрешите на Node входящий 64441/tcp для первого клиентского профиля. Порт открывается в Security Group Node, а не Controller.
  4. Ручные apt update, curl, unzip и отдельная установка Xray не требуются.

Шаг 1. Полностью подготовить Ubuntu как SG-Node

  1. Откройте Cluster на Controller.
  2. В карточке «Шаг 1» нажмите «Скопировать команду полной установки SG-Node».
  3. Подключитесь по SSH к чистой Ubuntu Node и запустите скопированную однострочную команду.
  4. Дождитесь успешного завершения и состояния STATUS=ready_to_connect в /etc/sg-node/install.env.

Полная команда устанавливает Agent, Worker, Xray, Nginx, Certbot, зависимости, службы и журналы. Она не создаёт карточку, не содержит enrollment token и не подключает Node к Cluster.

Шаг 2. Создать карточку Node

  1. Вернитесь в Cluster и нажмите «Добавить подготовленную SG-Node».
  2. Введите имя, роль и локацию. Публичный IP или домен можно оставить пустым — Agent попробует определить его по heartbeat.
  3. Нажмите «Создать карточку и новый токен».
  4. Откроется карточка Node с одноразовой командой подключения. Токен действует 30 минут и используется один раз.

Шаг 3. Подключить уже установленную SG-Node

  1. На странице карточки нажмите «Скопировать команду подключения».
  2. Запустите её на той же Node, где выполнен шаг 1.
  3. Команда проверит ready_to_connect, обновит Agent/Worker, зарегистрирует одноразовый token, запустит службы и отправит настоящий heartbeat.
  4. После принятого heartbeat страница обновится автоматически: использованная команда исчезнет, а шаг первого профиля станет доступным.
!

Не запускайте команду подключения на чистой Ubuntu вместо полной установки. При отсутствии /etc/sg-node/install.env она остановится и попросит сначала подготовить SG-Node.

Шаг 4. Убедиться, что Node действительно подключена

Карточка должна показать состояние «В сети», работающие Agent и Worker, свежий heartbeat, публичный адрес, платформу и версии компонентов.

До первого профиля — нормально

Xray и Nginx могут показывать «ожидает первого профиля», а серверная схема — «Первый профиль ещё не развёрнут».

Адрес не определён

В карточке введите реальный публичный IPv4 или домен без https:// и нажмите «Сохранить карточку». Не используйте Reality SNI как адрес Node.

Шаг 5. Развернуть первый VLESS REALITY

  1. На Node заранее разрешите входящий 64441/tcp.
  2. В блоке «Шаг 5 · Первый профиль» выберите существующего клиента.
  3. Проверьте публичный адрес Node, порт 64441, Reality target и Server Name / SNI.
  4. Нажмите «Проверить и развернуть».
  5. Worker выполнит проверку задания, xray run -test, backup, атомарное применение и rollback при ошибке.
  6. После завершения проверьте Xray, порт и реальное подключение клиента.
Первый профиль NodeПодтверждённая стартовая схема

VLESS REALITY · RAW/TCP · 64441 · XTLS Vision · fingerprint Firefox.

Повторное подключение и обслуживание

«Создать новую команду»

Используйте только для повторной регистрации, переноса сервера или ротации токена. Для обычной работающей Node эта кнопка не нужна.

«Отключить ноду»

Останавливает управление из Cluster, но не удаляет рабочий Xray-профиль с сервера.

«Удалить» карточку

Удаляет запись из Cluster. Xray, Nginx и конфигурация на удалённой Node автоматически не уничтожаются.

Команды обновления всех компонентов и удаления только Agent находятся в раскрывающемся блоке «События и обслуживание» карточки Node.

Типовые ошибки

Нет ready_to_connect

Проверьте /var/log/sg-node-full-install.log и /etc/sg-node/install.env. Карточку создавайте только после успешной полной установки.

Токен истёк

Нажмите «Создать новую команду» или «Создать команду переподключения» и используйте новую строку.

Agent/Worker работают, шаг 5 закрыт

Подождите новый heartbeat и обновление версии Xray. Проверьте systemctl status sg-node-agent, sg-node-worker и их journal.

Профиль есть, клиент не подключается

Проверьте 64441/tcp, публичный адрес, состояние Xray, журнал задания и совпадение Flow/fingerprint в ссылке.

i

Журналы Node: полная установка — /var/log/sg-node-full-install.log; подключение — /var/log/sg-node-connect.log; службы — journalctl -u sg-node-agent, sg-node-worker и xray.

INBOUND

Пять профилей SG-Panel

Названия показывают протокол и способ защиты. XTLS Vision является параметром REALITY, а не отдельным шестым профилем.

REALITY · без сертификата

Здесь находятся две схемы с маскировкой REALITY: обычный TCP и XHTTP.

TLS · нужен сертификат

Здесь находятся XHTTP через Nginx, Hysteria 2 и их совместный режим.

VLESS REALITYTCP · сертификат не требуется

Прямой VLESS с маскировкой REALITY. Поддерживает до трёх точек и режим XTLS Vision.

VLESS XHTTP-REALITYXHTTP · сертификат не требуется

XHTTP защищён REALITY и сейчас использует одну публичную точку и один Path.

VLESS XHTTP-TLSTCP/443 · TLS-сертификат

XHTTP проходит через Nginx. До трёх уникальных Path направляются на отдельные локальные Inbound Xray.

Hysteria 2UDP/QUIC · TLS-сертификат

До трёх независимых UDP Inbound с отдельными портами и auth для каждого клиента.

XHTTP-TLS + Hysteria 2TCP + UDP · общий сертификат

Одновременно запускает включённые XHTTP-TLS и Hysteria 2. Их настройки и ссылки остаются раздельными.

Цвет состояния: зелёная метка означает профиль, который работает на сервере сейчас. Янтарная карточка означает выбранный черновик; сервер переключится только после проверки и применения.

VLESS REALITY

REALITY и XTLS Vision — две разные настройки

REALITY защищает и маскирует внешнее соединение. Vision задаёт способ обработки VLESS-потока внутри этого соединения.

REALITY

Определяет server name, ключи REALITY, Short ID и параметры внешней маскировки. Профиль может работать с Vision или без него.

XTLS Flow

xtls-rprx-vision включает Vision. Пустой Flow означает стандартный VLESS через REALITY без Vision.

Стандартный VLESS

Flow отсутствует

Используйте для совместимости с уже выпущенными ссылками или клиентом, который не поддерживает Vision.

XTLS Vision — рекомендуется

Flow: xtls-rprx-vision

Рекомендуемый режим для VLESS REALITY + TCP при использовании совместимого клиента.

!

Flow должен совпадать на сервере и в клиентской ссылке. Если включить Vision только в клиенте, серверный пользователь останется без соответствующего Flow и подключение не заработает. SG-Panel меняет серверную конфигурацию и экспортируемые ссылки одновременно.

  1. Откройте Xray Server → Inbound и выберите значение в поле XTLS Flow.
  2. Нажмите «Проверить конфигурацию», затем «Сохранить и применить».
  3. Скопируйте новую ссылку или обновите подписку клиента. Старую ссылку с другим Flow не изменяйте вручную.

Ожидаемый результат: в серверном пользователе и клиентской ссылке присутствует одно и то же значение Flow. Существующая установка не переводится на Vision автоматически, чтобы не сломать ранее выданные ссылки.

VLESS XHTTP-TLS

До трёх Path через один TCP/443

Nginx принимает TLS на публичном порту и направляет каждый Path на собственный локальный TCP-listener Xray.

TCP/443→Nginx + TLS→Path 1 / Path 2 / Path 3→Xray

Локальные порты XHTTP не нужно открывать в Security Group. Наружу открывается только публичный TCP-порт, обычно 443.

VLESS XHTTP-REALITY

XHTTP с защитой REALITY

Этот профиль не использует обычный TLS-сертификат и не смешивается с Hysteria 2.

В текущей версии профиль использует одну публичную точку и один Path. Настройки других профилей сохраняются, но не входят в активный config.json.

HYSTERIA 2

До трёх UDP/QUIC Inbound

Каждый включённый экземпляр получает собственный UDP-порт, tag, клиентский auth, ссылку и QR-код.

PrimaryUDP/443BackupUDP/8443AltUDP/9443

Все используемые UDP-порты должны быть открыты в AWS Security Group. TLS-домен и сертификат общие для всех экземпляров.

MIXED

XHTTP-TLS + Hysteria 2

TCP и UDP работают одновременно и не конфликтуют, даже если номер порта совпадает.

TCP

XHTTP-TLS

До трёх Path через Nginx и один публичный TCP/443.

UDP

Hysteria 2

До трёх прямых UDP-портов: 443, 8443 и 9443.

CLIENTS

Активные и сохранённые ссылки

Переключение серверного профиля не удаляет ранее созданные параметры подключения.

Активные сейчасРаботают на сервере и входят в подписку.

Сохранённые, но неактивныеОстаются видимыми и доступными для копирования, но не работают до активации соответствующего профиля.

Имена Multi-Inbound формируются компактно: Имя/Primary, Имя/Backup, Имя/Alt. Протокол SG Client показывает отдельно.

SECURITY

TLS профилей и HTTPS панели

Это связанные, но разные задачи.

TLS профиля

Нужен для XHTTP-TLS и Hysteria 2. Сертификат участвует в клиентском соединении.

HTTPS панели

Защищает вход администратора, сессии и URL подписок. После переключения панель открывается в текущей вкладке.

REALITY и XHTTP-REALITY используют собственную схему защиты и не требуют обычного TLS-сертификата для клиентского соединения.

SECURITY → PANEL EXPOSURE

Как безопасно открыть административную панель

Этот блок выбирает архитектуру доступа и проверяет готовность. Он не заменяет настройку Cloudflare, DNS, AWS Security Group или firewall.

Текущая архитектура SG-Panel

Браузер→публичный Nginx→SG-Panel backend 127.0.0.1:8080

Python backend не публикуется напрямую. Публичное HTTP/HTTPS-соединение принимает Nginx и передаёт запрос локальному приложению SG-Panel.

i

Что делает SG-Panel: сохраняет выбранный режим, показывает текущий маршрут, проверяет доступные локальные признаки и выбирает допустимый источник IP посетителя. Что SG-Panel пока не делает: не создаёт DNS-записи, не меняет AWS Security Group или внешний firewall, не создаёт Tunnel, Access application и Access policy.

Режим 1. Direct through Nginx

Браузер→публичный Nginx :61443→127.0.0.1:8080

Это базовый режим: браузер обращается прямо к серверу. Поля Cloudflare hostname и Tunnel не нужны.

  1. Выберите Direct through Nginx.
  2. Проверьте, что backend слушает только 127.0.0.1:8080, а наружу открыт Nginx.
  3. Включите HTTPS. Для публичного сервера ограничьте порт своим IP через IP allowlist и внешний firewall.
  4. Нажмите «Сохранить режим и проверить готовность».

Ожидаемый результат: панель открывается по прямому адресу Nginx; Cloudflare-проверки не показываются как ошибки выбранного режима.

Режим 2. Cloudflare Proxy

Браузер→Cloudflare Proxy→публичный Nginx→127.0.0.1:8080

Cloudflare принимает внешний запрос и передаёт его на origin. Для HTTPS Proxy поддерживаются порты 443, 2053, 2083, 2087, 2096 и 8443. Стандартный порт SG-Panel 61443 обычным Cloudflare Proxy не обслуживается.

  1. Создайте в Cloudflare hostname, например panel.example.com, и включите для DNS-записи Proxy — orange cloud.
  2. Переведите HTTPS панели на поддерживаемый порт, обычно 8443, и сначала проверьте вход через hostname.
  3. Во внешнем firewall или AWS Security Group разрешите доступ к origin-порту панели только от сетей Cloudflare. Это называется origin lockdown.
  4. Повторно проверьте вход через Cloudflare в отдельном приватном окне.
  5. Только после реального ограничения origin включите подтверждение «Я уже ограничил origin во внешнем firewall».
  6. Сохраните режим. После обнаружения запроса через Cloudflare SG-Panel может использовать CF-Connecting-IP как исходный IP посетителя.
!

Не доверяйте CF-Connecting-IP при открытом origin. Пока сервер принимает прямые запросы из интернета, посторонний клиент может прислать похожий заголовок самостоятельно. Сначала закройте прямой доступ, затем подтверждайте origin lockdown.

Ожидаемый результат: hostname открывается через Cloudflare, выбранный порт поддерживается, в запросе видны признаки Cloudflare edge, а прямое обращение к origin заблокировано.

Режим 3. Cloudflare Tunnel + Access

Браузер→Cloudflare Access→Cloudflare Tunnel→локальный Nginx→127.0.0.1:8080

cloudflared устанавливает исходящее соединение с Cloudflare. Для самой панели не требуется публично открытый входящий порт, а Access выполняет дополнительную проверку пользователя до штатного входа SG-Panel.

  1. Создайте Tunnel в Cloudflare и установите cloudflared на Controller.
  2. Свяжите hostname панели с локальной точкой Nginx, указанной в конфигурации Tunnel.
  3. Создайте Cloudflare Access self-hosted application для этого hostname.
  4. Создайте Access policy, которая явно разрешает вход нужным пользователям или группам.
  5. Откройте hostname в отдельном приватном окне и убедитесь, что сначала появляется проверка Access, а затем логин SG-Panel.
  6. В SG-Panel укажите hostname и информационное имя Tunnel. Подтвердите «Я уже создал Cloudflare Access application и policy».
  7. Только после успешной проверки закройте публичный порт панели во внешнем firewall.

Ожидаемый результат: cloudflared работает, Access защищает hostname, панель доступна через Tunnel, а прямой публичный порт больше не требуется.

Что означают поля и индикаторы

Current route

Сохранённая архитектура доступа: Direct, Proxy или Tunnel. Это не автоматический переключатель Cloudflare.

Origin endpoint

Адрес и порт публичного Nginx. Backend рядом должен оставаться локальным.

Client IP source

Источник адреса посетителя. Для Direct используется прямой запрос; для защищённого Cloudflare-маршрута — CF-Connecting-IP.

Cloudflare hostname

Полное доменное имя панели в Cloudflare, а не IP и не URL с протоколом.

Cloudflare Tunnel name

Информационное имя уже созданного Tunnel. Ввод имени не создаёт Tunnel.

Cloudflare edge

Признаки того, что текущий запрос действительно прошёл через Cloudflare. Direct-запрос закономерно их не содержит.

Origin lockdown

Ручное подтверждение уже настроенного внешнего firewall. Переключатель сам правила не меняет.

Cloudflare Access

Ручное подтверждение уже созданных application и policy. Переключатель сам их не создаёт.

Безопасный переход без потери доступа

  1. Не закрывайте текущий рабочий маршрут и не удаляйте старое правило firewall.
  2. Полностью настройте новый hostname, Proxy или Tunnel.
  3. Проверьте новый вход в отдельном приватном окне, не закрывая текущую административную сессию.
  4. Убедитесь, что можете войти повторно, открыть Security и выполнить обычное действие в панели.
  5. Только после этого ограничьте origin или закройте старый публичный порт.
  6. Снова проверьте новый маршрут и только затем сохраните соответствующее подтверждение в SG-Panel.

Какой режим выбрать

Direct

Простой базовый доступ

Подходит для локальной сети, SSH-туннеля или жёсткого ограничения административного IP.

Proxy

Cloudflare перед origin

Подходит, когда Nginx остаётся публичным, но origin закрыт сетями Cloudflare.

Tunnel + Access

Закрытый административный вход

Предпочтительный вариант, когда публичный входящий порт панели не нужен.

Типичные предупреждения

61443 не поддерживается Proxy

Выбран обычный Cloudflare Proxy, но порт не входит в список HTTPS-портов Cloudflare. Используйте, например, 8443 или выберите Tunnel.

Cloudflare edge не обнаружен

Текущая страница открыта напрямую, DNS ещё не proxied или запрос не дошёл через Cloudflare. Проверьте hostname в отдельном окне.

cloudflared не обнаружен

Служба не установлена, не запущена или имеет другое имя. Проверьте Tunnel на Controller.

Access не подтверждён

Создайте self-hosted application и policy, проверьте внешний вход и только затем включите подтверждение.

ROUTING

Traffic Rules, Outbounds, DNS и GeoFiles

Четыре вкладки формируют единую серверную маршрутизацию Xray.

Traffic Rules

Определяют, какой трафик отправлять через конкретный Outbound, напрямую или в блокировку.

Outbounds

Описывают реальные выходы: direct, block, WARP и пользовательские узлы Xray.

DNS

Разрешает домены для правил и задаёт upstream-серверы, hosts и стратегию запросов.

GeoFiles

CASCADE

Полная настройка входного и выходного серверов

Cascade оставляет пользователю обычную ссылку входного сервера, но выпускает его трафик в интернет через вторую SG-Panel.

Клиент→Входной сервер→Выходной сервер→Интернет
Входной сервер

Принимает обычное клиентское подключение. Именно его ссылка или подписка выдаётся пользователю.

Выходной сервер

Создаёт отдельный управляемый VLESS REALITY-доступ и выпускает трафик в интернет.

Служебная ссылка

Передаётся только между двумя SG-Panel. Конечному пользователю она не нужна.

Перед началом

  1. Проверьте обычное подключение клиента к будущему входному серверу без Cascade.
  2. Убедитесь, что Xray на обоих серверах работает и публичный TCP-порт из служебной ссылки выхода доступен.
  3. В System → Status & Services задайте понятные имена серверов. Они будут показаны в схеме Cascade.

Шаг 1. Создать ссылку на выходном сервере

  1. Откройте Cascade на сервере, через который должен выходить интернет.
  2. В левой карточке «1. Создать ссылку» нажмите «Сделать этот сервер выходом».
  3. Панель сама создаст отдельный служебный VLESS REALITY-доступ.
  4. Нажмите «Скопировать ссылку». Если браузер при HTTP не разрешил Clipboard API и кнопка показывает «Выделено — нажмите Ctrl+C», нажмите Ctrl+C вручную.

Обычного клиента на выходном сервере специально создавать не нужно. UUID и REALITY-параметры служебного доступа создаёт SG-Panel.

Шаг 2. Вставить ссылку на входном сервере

  1. Откройте Cascade на входном сервере.
  2. В правой карточке «2. Вставить ссылку» вставьте служебную ссылку выхода.
  3. Нажмите «Подключить и проверить».
  4. Панель импортирует адрес, порт, UUID, REALITY public key, Short ID, SNI, fingerprint и Flow, затем выполнит настоящий тест полного маршрута.
  5. Успешный результат должен показать «Соединение работает» и внешний IP выходного сервера.

Шаг 3. Включить Cascade

  1. После свежей успешной проверки нажмите «Включить Cascade» один раз.
  2. Вверху страницы должен появиться статус «Cascade включён».
  3. Не создавайте Outbound, tag и Default Outbound вручную: SG-Panel сама назначает Cascade основным выходом.

Шаг 4. Выдать пользователю правильную ссылку

  1. На входном сервере нажмите «Открыть Clients».
  2. Выберите существующего обычного клиента либо создайте нового.
  3. Выдайте его активную ссылку или подписку входного сервера.
  4. Подключитесь и проверьте IP: сайт должен показать адрес выходного сервера.
!

служебную ссылку выхода пользователю не выдавайте. В пользовательской ссылке должен оставаться адрес входного сервера.

Почему слева всё ещё есть «Сделать этот сервер выходом»

После подключения текущей цепочки эта кнопка не нужна. Она используется только если данный сервер хотят сделать выходом для ещё одного входного сервера. Для обычной цепочки из двух серверов повторно нажимать её не следует.

Проверить, заменить или временно отключить

«Проверить ещё раз»

Используйте после перезагрузки выхода, изменения адреса или REALITY-параметров, ошибки соединения либо перед повторным включением.

«Заменить выходной сервер»

Создайте ссылку на новом выходе, раскройте этот блок на входе, вставьте новую ссылку, нажмите «Подключить и проверить» и проверьте новый IP.

«Отключить и вернуть Direct»

Возвращает основной выход на direct, но сохраняет импортированные параметры. Те же пользовательские ссылки продолжают работать через IP входного сервера.

Полностью удалить Cascade

Кнопка «Удалить Cascade» действует только на текущем сервере.

На входном сервере

Удаляется локальный Cascade Outbound и возвращается direct. Обычные клиенты, UUID, входные REALITY-ключи и сертификаты сохраняются.

На выходном сервере

Удаляется локальный служебный доступ Cascade. Обычные клиенты и активный серверный профиль не удаляются.

Для полной очистки цепочки удалите Cascade отдельно на входном и выходном серверах.

Cascade и Traffic Rules

Явные правила Routing выполняются раньше основного выхода Cascade. Поэтому выбранный сайт может идти через warp, direct или blocked, а весь остальной трафик — через Cascade. Правило создаётся на том сервере, где оно должно сработать.

Типовые ошибки

«Проверка не пройдена»

Проверьте адрес и TCP-порт служебной ссылки, Xray на выходе, Security Group/firewall, целостность ссылки, время серверов и не был ли служебный доступ создан заново.

«Включить Cascade» недоступна

Нужна свежая успешная проверка. Нажмите «Проверить ещё раз» и дождитесь результата с выходным IP.

Клиент перестал подключаться

Нажмите «Отключить и вернуть Direct», проверьте обычного клиента, затем повторно проверьте Cascade и журналы обоих серверов.

Сайт показывает IP входа

Переподключите клиента, проверьте статус «Cascade включён», отсутствие правила direct для тестового сайта и повторите проверку.

i

Главное правило: выход создаёт служебную ссылку, вход импортирует и проверяет её, а конечный пользователь всегда получает обычную ссылку из Clients входного сервера.

ROUTING → WARP

Российские сайты через Cloudflare WARP

Полный путь: создать WARP Outbound, проверить его отдельно, добавить два управляемых правила, применить конфигурацию и доказать маршрут контрольным сайтом.

WARP Outbound

Реальный выход Xray с тегом warp. Его создание ещё не направляет через WARP пользовательский трафик.

WARP Routing

Правила, которые решают, какие домены и IP использовать через warp, а какие оставить на обычном выходе direct.

Проверка WARP

Отдельный тест Outbound подтверждает, что Cloudflare доступен. Контрольное правило подтверждает, что Traffic Rules действительно выбирают этот выход.

Перед началом

  1. Подключение клиента к текущему серверу должно уже работать без WARP.
  2. В Routing → GeoFiles должны отображаться установленные geosite.dat и geoip.dat.
  3. Запишите публичный IP EC2. Он нужен для сравнения с адресом Cloudflare после проверки.

Шаг 1. Создать и проверить WARP Outbound

  1. Откройте Routing → Outbounds.
  2. В карточке WARP Outbound нажмите «Создать WARP». SG-Panel зарегистрирует учётные данные Cloudflare, соберёт native WireGuard Outbound Xray и проверит итоговый config.json.
  3. После создания статус должен стать «Активен», а тег Outbound — warp.
  4. Нажмите «Проверить WARP». Панель выполнит отдельный запрос через этот Outbound, не меняя рабочие правила клиента.
  5. Успешный результат показывает выходной IP Cloudflare. Это может быть IPv4 или IPv6; IPv6 здесь не является ошибкой.
!

Проверка WARP и маршрутизация — разные вещи. Статус «Активен» доказывает работоспособность Outbound, но пользовательский трафик начнёт идти через него только после создания и применения Traffic Rules.

Шаг 2. Выбрать российский пресет

  1. Нажмите «Открыть Routing» и выберите режим «Только выбранные сайты».
  2. Для одних российских доменных зон выберите «Только российские доменные зоны»: панель подставит geosite:tld-ru, а поле IP оставит пустым.
  3. Для широкого охвата выберите «Российские сайты и IP»: панель подставит geosite:category-ru и geoip:ru.
  4. category-ru уже включает tld-ru, поэтому добавлять обе категории одновременно не нужно.
  5. Нажмите «Проверить конфигурацию». Только после успешной проверки нажмите «Сохранить и применить».
geosite:category-ru→warp · priority 40+geoip:ru→warp · priority 41

Почему в широком пресете создаются два правила: поля Domain и IP внутри одного правила Xray объединяются логическим AND. Два отдельных правила дают нужную логику OR: через WARP проходит трафик, совпавший либо по домену, либо по IP.

Как добавить отдельный сайт

В режиме «Только выбранные сайты» добавьте условие новой строкой в подходящее поле, затем снова выполните проверку и применение.

Домены / Geosite

domain:example.ru — домен и его поддомены.
full:www.example.ru — только точное имя.
keyword:example — совпадение по части имени.
geosite:category-ru — категория из geosite.dat.

IP / GeoIP / CIDR

geoip:ru — категория из geoip.dat.
203.0.113.25 — отдельный IP.
203.0.113.0/24 — сеть CIDR.
Каждое условие вводится с новой строки, без запятых.

Шаг 3. Проверить созданные правила

  1. Прокрутите страницу до таблицы «Правила маршрутизации».
  2. Убедитесь, что правило с приоритетом 40 содержит domain: geosite:category-ru, выход warp и состояние «Включено».
  3. Убедитесь, что правило с приоритетом 41 содержит ip: geoip:ru, выход warp и состояние «Включено».
  4. Помните: меньшее число приоритета выполняется раньше. Защитные правила с приоритетами 10 и 20 должны остаться выше WARP.

Шаг 4. Доказать маршрут контрольным правилом

i

В выборочном режиме обычный сайт проверки IP может показать IP EC2 — это нормально: его домен не обязан входить в category-ru. Для однозначного теста временно направьте конкретный проверочный домен через WARP.

  1. В таблице правил нажмите «Добавить правило».
  2. Введите название WARP test — ifconfig.me.
  3. Укажите приоритет 39, выход warp и сеть tcp,udp.
  4. В поле «Домены» введите domain:ifconfig.me. Остальные условия оставьте пустыми.
  5. Нажмите «Проверить конфигурацию», затем «Создать правило».
  6. Переподключите клиент или откройте новую приватную вкладку и посетите ifconfig.me.
  7. Показанный адрес должен отличаться от публичного IP EC2 и соответствовать выходу Cloudflare, который показала кнопка «Проверить WARP».
  8. После подтверждения удалите временное правило WARP test — ifconfig.me.

Шаг 5. Проверить настоящий российский домен

  1. Оставьте только управляемые правила 40 и 41.
  2. Откройте 2ip.ru. В текущем комплекте GeoFiles этот домен попадает под российское правило.
  3. Ожидаемый результат: показан адрес Cloudflare/WARP, а не публичный адрес EC2; провайдер может определяться как Cloudflare.
  4. Откройте обычный зарубежный сайт проверки IP. При выборочном режиме он должен по-прежнему показывать IP EC2, если для него нет отдельного WARP-правила.

Если результат не совпал

Показывается IP EC2

Это нормально для домена, который не совпал с правилами. Проверьте контрольное правило, его состояние, выход warp и приоритет.

Категория не найдена

Откройте Routing → GeoFiles. Активные файлы должны содержать category-ru и ru. Панель не применит неисправный кандидат.

Правила есть, но старый маршрут сохраняется

Переподключите клиент, закройте старые вкладки или используйте приватное окно. Уже открытое HTTP/3 или TLS-соединение может некоторое время использовать прежний маршрут.

Сайт использует зарубежный CDN

Добавьте его домен отдельной строкой domain:.... Маршрут по geoip:ru сам по себе не охватит зарубежный адрес CDN.

ROUTING → GEOFILES

Фактически используемые geoip.dat и geosite.dat

Нейтральное состояние — не пустые поля, а установленный комплект Xray с реальными путями, размерами, датами и SHA-256.

  1. Откройте Routing → GeoFiles и проверьте активный источник и оба файла.
  2. Для обычной установки оставьте Installed Xray package. Это безопасное значение по умолчанию.
  3. Для смены источника явно включите редактирование и выберите поддерживаемый комплект, пользовательские HTTPS URL или локальные файлы.
  4. Нажмите «Проверить GeoFiles». SG-Panel проверит файлы и совместимость текущих Routing Rules.
  5. Только после успешной проверки примените комплект. При ошибке используется backup/rollback.

Ожидаемый результат: оба файла существуют, имеют ненулевой размер и SHA-256, а статус проверки показывает, что текущие правила могут быть с ними собраны.

XRAY SERVER → ДОПОЛНИТЕЛЬНО

Серверно-клиентские параметры без догадок

SG-Panel является источником параметров, которые зависят от сервера. SG Client получает их из управляемого JSON-профиля и не должен предлагать обычному пользователю придумывать Flow, ECH, fingerprint или CA PEM.

Что видит профиль REALITY

Параметры REALITY

В профиль передаются Server Name, public key, short ID, fingerprint клиента и Flow. Для TCP REALITY значение xtls-rprx-vision записывается серверному пользователю и в URI одновременно.

TLS certificate extras скрыты

ECH, SHA-256 сертификата и пользовательская CA/PEM не относятся к обычной проверке сертификата REALITY и не включаются в управляемый профиль.

!

Vision нельзя включать только в SG Client. Если Flow отсутствует на сервере или в профиле, локальное включение приведёт к несовместимости соединения.

Что видит профиль TLS

System CA — по умолчанию

Для сертификата публичного центра сертификации дополнительные поля не нужны. Клиент проверяет цепочку системным хранилищем и имя из Server Name/SNI.

verifyPeerCertByName

Ручное имя задаётся только для специальной схемы, когда имя подключения отличается от имени сертификата. В обычном режиме оно вычисляется автоматически.

Certificate SHA-256

Отпечаток рассчитывается из конкретного проверенного сертификата или передаётся администратором. SG-Panel не реализует опасный режим «получить с удалённого сервера и сразу доверять».

Пользовательская CA PEM

Нужна главным образом для частной CA. Импортируется полная цепочка без закрытого ключа; системные корневые сертификаты остаются включены.

ECH

Связанная серверно-клиентская пара

Владелец сервера создаёт echServerKeys и соответствующую клиентскую ECHConfig. Серверный секрет хранится только на Controller и никогда не экспортируется.

Получение клиентом

SG Client получает готовую ECHConfig из управляемого профиля либо проверенный DNS/DoH-источник. Пользователь не создаёт случайное значение самостоятельно.

Контекст: SG-Panel показывает ECH только там, где TLS обрабатывает непосредственно Xray. Для XHTTP-TLS и gRPC-TLS TLS завершается в Nginx, поэтому фиктивная ECH-настройка Xray не предлагается.

XHTTP Extra и FinalMask

XHTTP Mode и Extra

Auto и эффективный JSON {} означают стандартное поведение Xray. Server Extra попадает в серверный config, Client Extra — в профиль SG Client.

FinalMask

Выключено — рекомендуется. Опытный администратор может применить проверенный пресет или согласованные Server/Client JSON. Случайные примеры не применяются автоматически.

Управляемая подписка SG Client

  1. Откройте страницу клиента и скопируйте адрес SG Client · управляемый JSON v2.
  2. JSON содержит активные соединения, применимость каждого параметра, источник значения и признак серверного управления.
  3. SG Client должен предпочитать объект managedV2. Старый managed v1 сохранён только для совместимости.
  4. Для REALITY объект TLS помечается как неприменимый и не содержит ECH, pin или PEM.
  5. Для TLS клиент использует System CA по умолчанию и добавляет только значения, реально переданные SG-Panel.
◆

URL содержит секретный token пользователя. Не публикуйте его. Доступ к JSON можно отключить в Security → Subscription endpoint.

Безопасный порядок изменения

  1. Проверьте эффективные состояния и текущий Inbound.
  2. Нажмите «Включить редактирование».
  3. Введите только значения от администратора, SG-Panel или проверенного локального файла.
  4. Выполните Validate; SG-Panel проверит формат и итоговый config.json через xray run -test.
  5. После успеха сохраните и примените. При ошибке используется rollback.
  6. Повторно импортируйте/обновите профиль в SG Client и проверьте источник каждого значения.

Ожидаемый результат: обычный пользователь импортирует профиль и подключается без ручного поиска криптографических параметров; эксперт видит их источник и может изменить только разрешённые значения.
