# Cascade: входной и выходной SG-Panel

Документ относится к версии `v0.10.0-rc70`.

## Что делает Cascade

Cascade соединяет две самостоятельные SG-Panel в одну цепочку:

```text
Клиент → входной сервер → выходной сервер → Интернет
```

Пользователь подключается по обычной ссылке клиента **входного сервера**, но внешний сайт видит публичный IP **выходного сервера**.

Пример:

```text
Клиент → Frankfurt Entry → Virginia Exit → Интернет
```

- **Входной сервер** принимает клиентское соединение.
- **Выходной сервер** создаёт отдельный служебный VLESS REALITY-доступ для входного сервера.
- **Служебная ссылка** используется только внутри SG-Panel и не выдаётся конечному пользователю.
- **Routing вручную для самого Cascade не требуется**: после включения SG-Panel сама назначает выход Cascade основным.

## Перед началом

Проверьте следующее:

1. На обоих серверах установлена и работает SG-Panel одной совместимой версии.
2. Xray и Nginx на обоих серверах находятся в штатном состоянии.
3. Клиентская ссылка входного сервера работает без Cascade.
4. Публичный TCP-порт служебной ссылки выходного сервера доступен из интернета. Обычно это `443/tcp`, но ориентируйтесь на порт в созданной ссылке.
5. У серверов заданы понятные имена в `System → Status & Services`, например `Frankfurt Entry` и `Virginia Exit`.

## Пошаговая настройка

### Шаг 1. Создать служебный доступ на выходном сервере

1. Войдите в SG-Panel сервера, через который должен выходить интернет.
2. Откройте раздел **Cascade**.
3. В левой карточке **«1. Создать ссылку»** нажмите **«Сделать этот сервер выходом»**.
4. SG-Panel автоматически создаст отдельного служебного клиента VLESS REALITY.
5. После появления ссылки нажмите **«Скопировать ссылку»**.
6. Если браузер не разрешил автоматическое копирование при обычном HTTP, поле будет выделено. Нажмите `Ctrl+C` вручную.

Не создавайте обычного клиента на выходном сервере специально для Cascade. Управляемый служебный доступ создаётся самой панелью.

### Шаг 2. Подключить выход на входном сервере

1. Войдите в SG-Panel входного сервера.
2. Откройте **Cascade**.
3. В правой карточке **«2. Вставить ссылку»** вставьте служебную ссылку с выходного сервера.
4. Нажмите **«Подключить и проверить»**.
5. Панель импортирует адрес, порт, UUID, REALITY public key, Short ID, SNI, fingerprint и Flow.
6. SG-Panel создаст временную проверяемую конфигурацию, выполнит реальный VLESS REALITY-тест и попробует получить внешний IP через выходной сервер.

Успешный результат выглядит так:

```text
Соединение работает
Выходной IP: <IP выходного сервера>
```

### Шаг 3. Включить Cascade

1. После успешной проверки нажмите **«Включить Cascade»** один раз.
2. Вверху страницы должен появиться статус **«Cascade включён»**.
3. Кнопка управления изменится на **«Отключить и вернуть Direct»**.

После включения не создавайте Outbound и не меняйте `Default Outbound` вручную. Это делает Cascade.

### Шаг 4. Выдать обычную ссылку пользователю

1. На входном сервере нажмите **«Открыть Clients»**.
2. Выберите существующего клиента либо создайте обычного нового клиента.
3. Скопируйте его активную ссылку или подписку входного сервера.
4. Импортируйте её в клиентское приложение.

В ссылке должен быть адрес входного сервера. Адрес выходного сервера в пользовательскую ссылку не подставляется.

### Шаг 5. Проверить реальный результат

1. Подключитесь обычной ссылкой входного сервера.
2. Откройте сайт проверки IP.
3. Он должен показать публичный IP выходного сервера.

Если показывается IP входного сервера, нажмите в Cascade **«Проверить ещё раз»**, затем переподключите клиента.

## Что означает кнопка «Сделать этот сервер выходом» на входном сервере

После подключения текущей цепочки эту кнопку нажимать не нужно. Она нужна только если данный сервер хотят использовать как **выходной для третьего сервера**.

Например:

```text
Server A → Server B → Server C → Интернет
```

Для обычной цепочки из двух серверов достаточно одного служебного доступа на выходном сервере.

## Повторная проверка

Кнопка **«Проверить ещё раз»** нужна, если:

- выходной сервер перезагружался;
- изменился его публичный адрес;
- изменились REALITY-параметры;
- была ошибка соединения;
- вы хотите убедиться в маршруте перед повторным включением;
- внешний IP перестал совпадать с ожидаемым.

Повторная проверка не создаёт нового обычного клиента и не меняет пользовательские UUID.

## Замена выходного сервера

1. На новом выходном сервере откройте **Cascade**.
2. Нажмите **«Сделать этот сервер выходом»** и скопируйте новую служебную ссылку.
3. На входном сервере откройте **Cascade**.
4. Раскройте **«Заменить выходной сервер»**.
5. Вставьте новую ссылку и нажмите **«Подключить и проверить»**.
6. Убедитесь, что показан IP нового выхода.
7. Если Cascade не включён, нажмите **«Включить Cascade»**.
8. Проверьте обычную клиентскую ссылку входного сервера.
9. На старом выходном сервере нажмите **«Удалить Cascade»**, если старый служебный доступ больше не нужен.

Обычные клиенты входного сервера, их UUID и подписки при замене выхода сохраняются.

## Временно отключить и вернуть Direct

На входном сервере нажмите **«Отключить и вернуть Direct»**.

Результат:

- основной выход возвращается на `direct`;
- пользователи продолжают использовать те же ссылки входного сервера;
- сохранённые параметры выходного сервера остаются в панели;
- Cascade можно снова проверить и включить без повторного импорта ссылки.

## Полностью удалить Cascade

Кнопка **«Удалить Cascade»** действует только на том сервере, где её нажали.

### На входном сервере

- удаляется локальный Cascade Outbound;
- основной выход возвращается на `direct`;
- обычные клиенты, UUID, REALITY-ключи входного профиля и сертификаты не удаляются.

### На выходном сервере

- удаляется локальный служебный доступ Cascade;
- обычные клиенты и серверный профиль не удаляются.

Для полной очистки цепочки нажмите **«Удалить Cascade»** сначала на входном, затем на выходном сервере.

## Cascade и Routing

Cascade задаёт только основной выход для трафика, который не совпал с явным правилом.

Явные `Traffic Rules` выполняются раньше. Поэтому:

- правило `site → warp` может отправить выбранный сайт через WARP;
- правило `site → direct` может обойти Cascade;
- правило `site → blocked` заблокирует сайт;
- остальные соединения пойдут через Cascade.

Создавайте правило на том сервере, где оно должно сработать. При цепочке из двух серверов серверная маршрутизация на входе и выходе является двумя независимыми уровнями.

## Типовые ошибки

### «Проверка не пройдена»

Проверьте:

1. доступен ли адрес и TCP-порт из служебной ссылки;
2. работает ли Xray на выходном сервере;
3. не изменилась ли служебная ссылка после её копирования;
4. нет ли лишних пробелов или переносов при вставке;
5. разрешён ли порт в AWS Security Group и firewall;
6. совпадает ли время на обоих серверах;
7. не был ли служебный доступ удалён или создан заново.

После исправления нажмите **«Проверить ещё раз»**.

### Кнопка «Включить Cascade» недоступна

Сначала должна пройти свежая успешная проверка. Нажмите **«Проверить ещё раз»** и дождитесь результата с выходным IP.

### Клиент не подключается после включения

1. Убедитесь, что до включения работала обычная ссылка входного сервера.
2. Нажмите **«Отключить и вернуть Direct»**.
3. Проверьте клиента в Direct.
4. Повторно проверьте Cascade.
5. Посмотрите `System → Logs & Diagnostics` на обоих серверах.

### Сайт показывает IP входного сервера

- переподключите клиент после включения Cascade;
- убедитесь, что статус страницы — **«Cascade включён»**;
- проверьте, нет ли правила `direct` для проверяемого сайта;
- нажмите **«Проверить ещё раз»**;
- сравните IP в панели с результатом сайта.

### Ссылка не копируется кнопкой

При HTTP некоторые браузеры ограничивают Clipboard API. SG-Panel использует резервное копирование. Если кнопка показывает **«Выделено — нажмите Ctrl+C»**, нажмите `Ctrl+C` вручную.

## Что Cascade не меняет

Настройка, отключение и удаление Cascade не должны самовольно менять:

- обычных клиентов;
- UUID клиентов;
- REALITY private/public keys активного входного профиля;
- TLS-сертификаты;
- подписки;
- GeoFiles;
- настройки SG Client.
