# Формы, контекстный JSON и обязательная проверка

SG-Panel хранит управляемую конфигурацию в SQLite и формирует из неё итоговый `config.json` Xray. Обычные формы и JSON-редакторы работают с одной моделью данных.

## Главный принцип

Любое изменение конфигурации выполняется последовательно:

1. изменить параметры через форму или JSON-редактор;
2. нажать **«Проверить конфигурацию»**;
3. дождаться успешной проверки кандидата;
4. нажать **«Сохранить и применить»**.

До успешной проверки кнопка сохранения заблокирована.

Проверка:

1. создаёт временную копию рабочей SQLite;
2. применяет черновик только к временной базе;
3. проверяет структуру и связи между объектами;
4. формирует полный итоговый `config.json`;
5. выполняет `xray run -test`;
6. возвращает подписанное подтверждение проверки.

Рабочая SQLite, активный файл Xray и запущенная служба во время проверки не изменяются.

Если после проверки изменить хотя бы одно поле, сохранение снова блокируется. Проверку также нужно повторить, если конфигурация была изменена в другой вкладке или другим администратором. Подтверждение действует 15 минут.

Автосохранения нет.

## Где доступен редактируемый JSON

### Пользователи

На странице **Clients → Clients** ссылка **Пользователи JSON** открывает полный массив:

```json
{
  "users": [
    {
      "name": "Sergey",
      "uuid": "...",
      "enabled": true,
      "comment": "Основной телефон",
      "expiryAt": null,
      "subscriptionEnabled": true
    }
  ]
}
```

JSON включает активных и отключённых пользователей. Для существующей записи SG-Panel сохраняет внутренний ID, токен подписки и счётчики, если совпадает UUID или имя. При переименовании ссылки на пользователя в Routing обновляются. Если удалённый пользователь был единственным ограничением правила, правило отключается — оно никогда не превращается молча в правило для всего трафика.

### Inbound

На странице **Inbound** ссылка **Inbound JSON** открывает объект основного управляемого inbound с тегом:

```text
vless-reality-in
```

Дополнительные Hysteria 2 Inbound управляются через Hysteria Studio. Дополнительные VLESS XHTTP-TLS Inbound управляются через Multi-XHTTP Studio. Их название, tag, listen, порт, Path и auth нельзя менять через Inbound JSON: это предотвращает рассинхронизацию SQLite, Nginx, клиентских ссылок и подписок. Полный Generated Config показывает все включённые экземпляры только для просмотра и экспертной проверки. В смешанном профиле там одновременно видны обе семьи; дополнительные экземпляры по-прежнему изменяются только в соответствующих Studio-блоках.

В JSON видны пользователи, transport, REALITY/TLS и дополнительные параметры Xray. Служебные данные интерфейса хранятся в `_sgPanel` и не передаются Xray.

### Outbounds

Для пользовательского выхода доступны:

- форма;
- JSON конкретного outbound;
- создание нового outbound из JSON.

Неизвестные поля, например `sockopt`, `mux` и новые параметры Xray, сохраняются при последующем редактировании через форму.

### Routing

Доступны:

- форма отдельного правила;
- JSON отдельного rule;
- JSON всего объекта `routing`;
- `balancers` и правила с `balancerTag`.

Полный Routing JSON заменяет управляемый список правил только после успешной проверки.

### DNS

Ссылка **DNS JSON** открывает:

- глобальные настройки DNS;
- активные DNS-серверы;
- `hosts`;
- служебные метаданные имени, приоритета и состояния.

Включённый DNS без активного сервера не пройдёт проверку.

### Cloudflare WARP

После создания WARP доступна ссылка **WARP JSON**. Редактор показывает WireGuard outbound и блок `_sgPanel`:

```json
{
  "enabled": true,
  "routeMode": "selected",
  "selectedDomains": [
    "domain:example.com"
  ]
}
```

Secret key остаётся локально в панели. Перед сохранением WARP нормализуется, а полный конфиг проверяется Xray. При создании и пересоздании точные сгенерированные ключи и outbound сначала помещаются во временную SQLite-копию; постоянный `wgcf.json` и рабочая база записываются только после успешного `xray run -test`. Удаление WARP также предварительно проверяется на временной базе.

### Полный config.json

На странице **Xray Config** доступен полный редактируемый документ. Он синхронизирует обратно в GUI:

- основной Inbound;
- пользователей и UUID;
- Outbounds;
- Routing и Balancers;
- DNS;
- log и Stats API.

Дополнительные верхнеуровневые секции и неизвестные поля сохраняются.

## Блок `_sgPanel`

`_sgPanel` хранит данные интерфейса, которых нет в формате Xray:

- понятное имя;
- приоритет;
- enabled/disabled;
- публичный адрес;
- срок действия пользователя;
- параметры GUI для WARP и других разделов.

Перед `xray run -test` и записью рабочего конфига эти блоки удаляются.

## Что происходит после нажатия «Сохранить и применить»

После успешной проверки SG-Panel:

1. убеждается, что форма не менялась после проверки;
2. убеждается, что рабочая конфигурация не изменилась параллельно;
3. записывает данные в SQLite;
4. повторно формирует рабочий `config.json`;
5. создаёт резервную копию;
6. заменяет конфиг атомарно;
7. перезапускает Xray;
8. при ошибке выполняет откат.

## Generated Config

Generated Config — это отдельный read-only просмотр фактически сформированного файла Xray. Он не заменяет контекстные редакторы и не используется для скрытого автосохранения.

## Ограничения

- визуальные формы охватывают только поддерживаемые SG-Panel поля;
- новые поля Xray можно сохранить через JSON;
- WARP JSON доступен только после создания WARP-учётных данных;
- внешние операции регистрации WARP и выпуска сертификата имеют собственный живой журнал и не являются обычным JSON-сохранением.
