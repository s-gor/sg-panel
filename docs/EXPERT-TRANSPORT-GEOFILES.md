# Дополнительные параметры, управляемый SG Client и GeoFiles

Документ относится к SG-Panel `v0.10.0-rc70`.

Настройки разнесены по функциональным разделам:

```text
Xray Server → Дополнительно
Routing → GeoFiles
Клиентский доступ → SG Client · управляемый JSON v2
```

## Главный принцип

SG-Panel является источником параметров, которые зависят от серверной конфигурации. Обычный пользователь SG Client не должен искать или придумывать ECH, certificate SHA-256, CA PEM, XTLS Flow либо связанные Server/Client JSON.

Управляемый профиль содержит:

- активные соединения;
- применимость параметров для каждого соединения;
- источник значения;
- серверно-управляемые поля;
- разрешённый экспертный override только там, где это безопасно.

## REALITY

Для REALITY экспортируются только применимые значения:

- Server Name;
- Reality public key;
- short ID;
- fingerprint клиента;
- spiderX;
- XTLS Flow.

ECH, SHA-256 TLS-сертификата и CA PEM не экспортируются. Объект TLS в managed v2 явно помечается как неприменимый.

Для VLESS REALITY + TCP значение `xtls-rprx-vision` должно одновременно находиться в серверной записи пользователя и в клиентском URI. SG Client не должен включать Vision локально, если Flow отсутствует в профиле.

## TLS

### System CA

По умолчанию SG Client использует системное хранилище доверия и проверяет имя из Server Name/SNI. Для обычного сертификата публичной CA пользовательский PEM не требуется.

### verifyPeerCertByName

Ручное значение используется только в специальной схеме, когда имя подключения отличается от имени сертификата. В обычном режиме SG-Panel передаёт автоматическое значение из Server Name.

### Certificate SHA-256

Отпечаток рассчитывается из конкретного локального сертификата либо вводится по данным администратора. SG-Panel не реализует «получить с удалённого сервера и сразу доверять». Сначала отпечаток сравнивается с доверенным источником, затем передаётся клиенту.

### Пользовательская CA PEM

Нужна прежде всего для частной CA. SG-Panel:

- принимает полную PEM-цепочку;
- запрещает закрытые ключи;
- проверяет структуру через OpenSSL, если он доступен;
- сохраняет SHA-256 и источник;
- оставляет системные корневые сертификаты включёнными.

## ECH

ECH требует настоящей связанной пары:

- `echServerKeys` остаётся только на Controller;
- клиент получает `echConfigList` либо проверенный DNS/DoH-источник;
- серверный секрет никогда не попадает в URI, подписку или managed JSON.

ECH показывается только там, где TLS обрабатывает непосредственно Xray. В XHTTP-TLS и gRPC-TLS SG-Panel завершает TLS в Nginx, поэтому Xray ECH для этих схем не предлагается.

## XHTTP Extra

`Auto` и эффективный JSON `{}` оставляют стандартное поведение Xray. Server Extra попадает в серверный `config.json`, Client Extra — в URI и управляемый профиль.

## FinalMask

FinalMask по умолчанию выключен и не добавляется ни в серверный config, ни в клиентский экспорт. Опытный администратор может применить:

- проверенный пресет SG-Panel;
- JSON администратора;
- согласованные Server/Client JSON.

Случайные примеры не применяются автоматически.

## Управляемая подписка SG Client

На странице клиента показаны два адреса:

1. стандартная Base64-подписка;
2. `?format=json` — управляемый JSON.

JSON-ответ содержит:

- `managed` — совместимый профиль v1;
- `managedV2` — точный профиль по каждому соединению;
- `managedPreferred: "managedV2"`;
- заголовок ответа `X-SG-Managed-Profile: v2`.

SG Client должен предпочитать `managedV2`. URL содержит секретный token пользователя и не должен публиковаться.

## Безопасный порядок изменения

```text
изменить только нужные значения
→ нажать «Проверить и применить»
→ проверить модель и итоговый config.json
→ xray run -test
→ применить или автоматически вернуть прежние значения при ошибке
→ обновить профиль в SG Client
```

## Routing → GeoFiles

GeoFiles относятся к маршрутизации. Панель показывает фактически активную пару `geoip.dat` и `geosite.dat`: источник, пути, размеры, даты, SHA-256, распознанное семейство, количество категорий и результат последней проверки.

Доступны:

- встроенный комплект SG Client;
- Loyalsoldier;
- RunetFreedom;
- RoscomVPN;
- два пользовательских HTTPS URL;
- загрузка двух файлов через браузер либо пути к локальной паре на сервере.

`geoip.dat` и `geosite.dat` всегда рассматриваются как единый комплект. Проверка выполняется до любого изменения рабочих файлов:

1. проверяются минимальный размер, SHA-256 и структура protobuf;
2. из каждого файла считываются фактически существующие категории;
3. строятся полный будущий Routing и полный будущий Xray config;
4. полный candidate запускается через `XRAY_LOCATION_ASSET=<staging> xray run -test`;
5. только после успешного результата создаётся новое поколение и начинается commit.

Категория `category-ads-all` не является обязательной. Комплект без неё может быть полностью исправным. Но если полный будущий config ссылается на отсутствующую категорию, применение жёстко блокируется с точным перечнем ссылок.

SG-Panel никогда автоматически не удаляет `geoip:` / `geosite:` ссылки, не урезает условия и не отключает пользовательские правила. Администратор должен исправить Routing либо выбрать совместимый комплект. Для источника RoscomVPN доступен явный серверный preset: он добавляет только реально существующие категории Direct, необязательный Block и финальный Direct. Пользовательские WARP, Cascade и внешние VLESS outbounds не изменяются.

Каждое поколение хранится в `/var/lib/sg-panel/geofiles/sets/<generation>/` вместе с `manifest.json` и проверенным `config.json`. Во время commit Xray останавливается, оба файла заменяются как одна транзакция, затем выполняются финальный `xray run -test`, restart и обязательная проверка `xray.service active`.

Rollback восстанавливает старую пару GeoFiles, прежний `config.json`, Routing settings, Routing Rules, WARP settings и полный `geofiles_settings`. Откат считается успешным только после проверки восстановленного config и подтверждения активной службы Xray. Ошибка restart не скрывается.

Флаги стран используют только независимую базу `/opt/xpanel-mvp/assets/geoip/sg-country-geoip.dat`. Активный routing `geoip.dat` никогда не используется как fallback для определения стран.

GeoFiles привязаны к серверу. Controller хранит свою generation, каждая SG-Node — свою. Controller передаёт Node точную проверенную пару через авторизованный endpoint, но Node локально повторно сверяет SHA-256, разбирает категории, проверяет свой полный config, применяет поколение и возвращает manifest и результат через Agent.
